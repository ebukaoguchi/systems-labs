## Three things to know before you teach it

**The prompt wording differs between the requirements slide and the code.** The requirements slide's menu mock ends with "Enter your choice:". The live-coding slides and the complete program prompt with "Enter choice: ". The shipped `menuDrivenCalculator.cpp` follows the code. Students transcribing from the requirements slide will produce the longer prompt; both are correct behaviour, but autograders and sample-output comparisons should be set to the code's wording.

**There are two different `displayMessage()` programs in the deck.** The review slide's version prints "Welcome to CIS 123!"; the prototypes slide's complete program prints "Hello, students!". They are separate examples making separate points (what a function is; then how prototype, call, and definition fit together). The shipped `displayMessage.cpp` follows the second, complete program. If a student asks why the message changed, that is the answer — but you may prefer to flag it before they do.

**`a` and `b` in `main()` are read only for choices 1–4, deliberately.** The `if (choice >= 1 && choice <= 4)` guard around the operand prompt means that on Exit or an invalid choice the variables are never read and never used — the `switch` cases that consume them are exactly the guarded ones. Students reliably ask why the program does not ask for numbers before showing the exit message; the deck itself poses the question. It is also the honest place to mention that the variables are uninitialised on the paths that skip the prompt, and safe only because those paths never touch them.

## The file-persistence extension (Milestone 8)

`menuDrivenCalculatorWithFiles.cpp` is the instructor's own extended version of the calculator, supplied as the follow-on to the deck program and subsequently folded into the deck itself, in the closing "Additional C++ Code Examples" appendix, alongside the if/else and value-returning forms. Relative to `menuDrivenCalculator.cpp` it changes four things: each operation computes a `result` variable and calls `saveResult(a, b, op, result)` after printing; `saveResult` appends one formatted line to `results.txt` (`ios::app`) and confirms with "Result saved successfully!"; a fifth menu option calls `viewResults()`, which prints the file's lines under a SAVED RESULTS header, or "No saved results found." when the file does not exist yet; and Exit moves from 5 to 6. Two classroom notes. First, `results.txt` is created in the program's working directory, which under some IDEs is the project folder and under others the build folder — students who "lose" their file have usually found this distinction. Second, the supplied text of this program used typographic (curly) quotation marks in place of ASCII quotes throughout; they were normalised to straight quotes in the shipped file, with no other alteration. That is worth thirty seconds if your students ever paste code out of a word processor or a chat window: the compiler error points at the string literal, never at the quote character that causes it.

**The if/else variant.** `menuDrivenCalculatorIfElse.cpp` is the same extension with its menu dispatch rewritten as an `if` / `else if` chain, supplied by the instructor for classes that prefer it over `switch`. Its observable behaviour is identical — verified by running the same scripted session against both forms and comparing output and the saved file line for line. The pair is most useful side by side: the `switch` version shows the menu as a table of cases, the chain version shows it as a sequence of tests, and the operand prompt's range guard (`choice >= 1 && choice <= 4`) is something only the chain form could express — which is precisely the trade-off the branching lab's comparison table names. The variant's supplied text carried the same typographic quotes as the extension's, normalised the same way.

**The value-returning variant.** `menuDrivenCalculatorValueReturning.cpp` is the instructor-supplied third form: value-returning operations, `if` / `else if` dispatch, no file saving. The design inversion to point at is the zero guard's address — in the deck calculator it lives inside `divide()`, here it sits in `main()` before the call, because a function whose whole job is to return a quotient has no business also owning the error message; `divide()` itself would return `inf` on a zero divisor if called unguarded, which is safe through this menu (operands are only read for choices 1–4, and choice 4 is the guarded path) and worth one sentence if a student proposes calling it from somewhere else. Supplied text carried the same typographic quotes, normalised the same way.

## The decimal-input failure, and the two hardened forms (Milestone 9)

The failure analysis, the `double` solution, and the input-validation pattern in this milestone were supplied by the instructor as teaching material for this module, and now also stand in the deck itself: the revised deck's two added slides (after the calculator's sample runs, before the exercise) present the failure and both solutions in short form. The two programs were assembled from the full material and verified as described in the Verification section. Staging notes:

- Reproduce the hang live only under a timeout or with output redirected — in two seconds the unmodified calculator produced over eleven million lines. The diagnostic details students should extract: `a` received 40 (the integer part), `b` was set to 0 (since C++11 a failed arithmetic extraction writes 0 to its target), the stream's failure state makes every subsequent extraction a no-op, and `choice`, never re-read, pins the loop. The phantom `Result: 40` is the tell that `b` was zeroed rather than left alone.
- Guarding the operands read alone (the form in which the validation pattern was supplied) fixes the decimal case but not a letter typed at the choice prompt, which fails that read the same way and hangs identically. `menuDrivenCalculatorHardened.cpp` therefore applies the same test-clear-discard pattern to the `choice` read as well; that extension of the supplied pattern is deliberate and is the version to hand out.
- The `double` form's `divide()` prints "Cannot divide by zero!" — with the exclamation mark, as supplied; the other calculator forms print the same message without it. Kept as written in each file; if the inconsistency will bother your students, it is a one-character edit per file, and catching it is a reasonable spot-check exercise.
- `continue` in the hardened form jumps to the `do-while` condition, not to the top of the loop body directly — worth one question in class, since the menu reprints because the condition passes, not because the loop restarts blindly.

## Running the session

- Keep the "Think Before You Code" pass intact. The seven design questions (which jobs become functions, what each receives, `void` or return, which function shows the menu, how the loop repeats, where the zero guard lives) are where the lab's actual content sits; the three live-coding parts are the answers being typed.
- The `do-while` choice deserves its thirty seconds: the menu must display at least once before any choice exists, which is the whole argument for testing at the bottom.
- In `divide()`, students may propose checking `b` in `main()` instead. The deck's design — the guard inside the function that divides, with an early `return;` — is the modular answer, and it sets up the contrast with the exercise, where the calculations return values and `main()` owns the display.
- Expected calculator behaviour worth demonstrating live beyond the deck's samples: an invalid choice (7) prints "Invalid choice, try again" and the menu repeats; only 5 exits.

## Verification

Both accompanying programs were compiled with `g++ -std=c++17 -Wall -Wextra` without warnings and run before publication. The calculator was driven through a scripted session covering every path: add (10, 20 → Result: 30) and divide-by-zero (10, 0 → "Cannot divide by zero"), reproducing the deck's two sample runs exactly; divide (10, 4 → Result: 2.5); invalid choice (7 → "Invalid choice, try again", menu repeats); and exit (5 → "Exiting program..."). `displayMessage.cpp` prints "Hello, students!", as its deck example states. The exercise's example arithmetic was checked by hand: the average of 80, 90, 100 is 90, matching the deck. The extension program was likewise compiled clean (`g++ -std=c++17 -Wall -Wextra`, after the quote normalisation described above) and verified in an empty working directory: viewing before any save prints "No saved results found."; a scripted session (add 10 and 20; divide 10 by 0; divide 10 by 4; an invalid choice; view; exit) saved exactly two lines to `results.txt` — `10 + 20 = 30` and `10 / 4 = 2.5`, with no line for the refused division — and the view option read both lines back. The if/else variant passed the same checks: compiled clean after the same quote normalisation, "No saved results found." on a first view, and the identical scripted session producing identical output and an identical `results.txt`. The value-returning variant was compiled clean after the same normalisation and run through every operation: add (10, 20 → 30), subtract (10, 20 → −10), multiply (6, 7 → 42), divide by zero refused from `main()`, divide (10, 4 → 2.5), invalid choice, and exit. The Milestone 9 failure was reproduced against the shipped deck calculator: fed choice 1 and the operands `40.5 45.6`, it had to be killed by a two-second timeout after printing the menu 1,402,451 times, every cycle reporting Result: 40. Both hardened forms compiled clean with the same flags; the `double` form gives 40.5 + 45.6 = 86.1, 10 / 4 = 2.5, and refuses 5 / 0; the input-hardened form gives the same results, rejects letters at both the operands prompt and the choice prompt with "Invalid input! Enter numbers only.", recovers to complete a valid calculation afterwards, and exits normally.
